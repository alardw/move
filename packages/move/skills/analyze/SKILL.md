# Analyze — Component Research & Analysis

Research how existing UI libraries implement a component, then write an analysis report as a persistent artifact.

---

## How to Run

**Input:** A component name or description (e.g. "ColorPicker", "layout helpers like Stack and Grid").

**Output:**
- `{Name}.analysis.md` written next to the component at `src/components/{category}/{Name}/{Name}.analysis.md`
- Stdout summary of findings and recommendations

**Two stages:**
1. **Research report** — Compare up to 5 libraries, output findings. Always runs first.
2. **Recommendations** — Concrete recommendations for Move implementation.

---

## Process

### Step 1 — Research (max 5 libraries)

**Baseline (pick the 3 most relevant):**

| Library | When to include |
|---------|----------------|
| Radix UI | Component has accessibility/interaction complexity |
| shadcn/ui | Component is common (Button, Dialog, etc.) |
| Mantine | Component needs rich props/variants |
| Chakra UI | Component is a layout or style primitive |
| MUI | Component needs enterprise-level features |

**Specialists (up to 2):** Only if a dedicated library is clearly better (TanStack Table, react-day-picker, cmdk, etc.).

### Step 2 — Capture per library

Just these 3 things:
1. **Props table** — name, type, default (skip obvious HTML pass-throughs)
2. **Composition** — monolithic or compound? What sub-components?
3. **Standout feature** — one thing this lib does better

### Step 3 — Write analysis report

Write `src/components/{category}/{Name}/{Name}.analysis.md`:

```markdown
<!-- Generated by /analyze | Date: {ISO timestamp} -->
# {Name} — Library Analysis

### Quick Comparison

| | Lib A | Lib B | Lib C |
|---|---|---|---|
| **Props** | ... | ... | ... |
| **Compound** | ... | ... | ... |
| **Standout** | ... | ... | ... |

### Props Detail

#### Lib A — {name}
| Prop | Type | Default |
|------|------|---------|
| ... | ... | ... |

```tsx
<Example />
```

(repeat for each lib)

### Recommendations for Move

1. **Components to build:** List with one-line descriptions
2. **Props consensus:** Which props appear across most libs
3. **Composition:** Compound vs monolithic recommendation
4. **Animation:** What needs motion (if anything)
5. **Component class:** Recommended class from spec-type
6. **Default candidates (not decisions):** proposed runtime/demo defaults with confidence
7. **Key decisions:** Anything that needs user input before spec creation
```

### Step 4 — Output summary

Print a concise summary to stdout with key recommendations.

---

## Efficiency Rules

- **Max 5 libraries total** (3 baseline + up to 2 specialists)
- **One web search per library** — fetch the component's doc page, extract, move on
- **Skip obvious stuff** — don't research RTL, bundle size, dependencies unless relevant
- **Keep it shallow** — props table + one minimal code snippet per lib
- **Don't over-research** — the goal is informed decisions, not exhaustive documentation

## Analysis report rules

- Report includes timestamp in header comment
- Report lives with the component as research provenance
- Report is informational, not gating — the spec is the authority
- Analyze may propose **default candidates** only. It must not finalize defaults; final defaults are approved in `/spec`.
- If analyzing multiple related components, produce one report covering all, then separate recommendations per component
