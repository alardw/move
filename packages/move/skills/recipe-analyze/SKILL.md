# Recipe Analyze — Pattern Research & Composition Mapping

Research how a flow or layout pattern is built in real apps and UI libraries,
then map it onto Move components. Writes an analysis report as a persistent
artifact. Informational, not gating — the spec is the authority.

Unlike `component-analyze` (which studies a single primitive's API), this studies
a **pattern** (a sign-in flow, a filterable data table, an app shell) and answers:
what does this flow need, and which Move components compose it?

---

## How to Run

**Input:** A recipe name or pattern description (e.g. "SignIn", "a filterable
data table with search, sort, and pagination").

**Output:**
- `{Name}.analysis.md` written next to where the recipe will live
  (`packages/move/recipes/{groupSlug}/{Name}.analysis.md`).
- Stdout summary of the recommended composition and behaviors.

---

## Process

### Step 1 — Research the pattern (max 4 sources)

Pick the most relevant of: shadcn/ui blocks, Mantine, Chakra, MUI templates,
and well-known app patterns (Linear, Stripe, Vercel dashboards). For each:
1. **Structure** — what regions/steps the flow has.
2. **States** — loading, empty, error, validation, success.
3. **Standout** — one thing this source does well.

### Step 2 — Map onto Move components

Translate the pattern into Move primitives (this becomes the spec's
`composition`):
- Layout → Stack, Grid, Align, Card
- Forms → FormField, InputText, Password, Select, Checkbox, Button
- Data → Table, List, Badge, Pagination, EmptyState
- Overlays → Dialog, Drawer, Popover, Dropdown
- Feedback → Alert, Toast, Skeleton, Loader

Flag any region the current Move set can't cover cleanly (a gap worth noting).

### Step 3 — Write the analysis report

Write `{Name}.analysis.md`:
```markdown
<!-- Generated by /recipe-analyze | Date: {ISO timestamp} -->
# {Name} — Pattern Analysis

### How others build it
| | Source A | Source B | Source C |
|---|---|---|---|
| **Structure** | ... | ... | ... |
| **States** | ... | ... | ... |
| **Standout** | ... | ... | ... |

### Recommended Move composition
- {component} — {what it covers}

### Recommended behaviors (spec candidates)
- {testable behavior}

### Recommended integration points
- {id} — {what the consumer wires}

### Recommended labels
- {key} — {default copy}

### Gaps / key decisions
- {anything needing a Move component that doesn't exist, or a decision before spec}
```

### Step 4 — Output summary

Print the recommended composition, behaviors, and any gaps to stdout.

---

## Rules

- **Max 4 sources** — informed decisions, not exhaustive documentation.
- **One search per source** — fetch, extract structure/states/standout, move on.
- **Output feeds the spec** — composition / behaviors / integration points /
  labels are framed as spec candidates, not final decisions.
- **Informational, not gating** — `/recipe-create-spec` finalizes everything.
- **Name the gaps** — if the pattern needs a primitive Move lacks, say so; that's
  a library signal.
